# Agent 开发工程师简历评估

## 使用目标与默认岗位

主要读者是**正在学习这些技术的面试官**。第一部分的首要目标是让面试官形成全面、准确的技术理解，能解释原理、理解工程取舍，再用于听懂和追问候选人的回答。不能把知识讲解压缩成候选人评分标准、答案关键词或考点清单，也不默认面试官已经熟悉候选人的技术栈。

用户主要招聘 Agent 开发工程师；没有 JD 时按此岗位继续，不要求用户先补齐 JD。不能擅自设定资深等级、业务行业、必需技术栈或录用门槛。用户给出 JD、级别、面试时长或重点后，以这些具体要求调整。

默认完整交付两个主体：**简历知识与技术点详细展开**、**从浅到深的技术与项目面试题及考核方向**。不要用整体评价、关键词列表、泛化题库或简历润色替代这两个主体。用户只要局部内容时按其范围输出。

## 先建立简历证据索引

- 必须实际读取简历正文。附件不可取得、扫描件无法识别或正文不全时，明确覆盖范围；可以评估已读部分，不编造遗漏内容。
- 给项目编号 P1、P2 等，给技术点编号 T1、T2 等。保留简历原称与必要短引文，记录所属项目、页码或小节（仅在确实可定位时）。
- 合并同义词，但不要漏掉技能栏和项目里的技术。列明覆盖清单：技术点、来源、与岗位的关系、展开位置或合并位置。技术太多时按关联分组，核心技术详解，辅助技术仍须说明用途、机制和核验点。
- 严格分开三类内容：①简历声称及原文；②通用技术解释；③待面试验证的能力。列出名称不等于掌握，团队项目不等于本人主导，简历没写不等于不会。
- 对吞吐、准确率、延迟、成本等数字记录原始单位、基线、测量环境、样本和本人贡献；缺失项标成待核实，不能替候选人补全。
- 逐字段区分“已给出”和“未给出”。例如“准确率从70%提高到90%”已经给出指标名称、百分比单位、起止数值；未知的是准确率定义、评测样本、基线版本和测量条件，不能统称“基线、单位全部缺失”。如计算增幅，区分增加20个百分点与相对提升约28.6%，不要混用。

## 主体一：知识和技术点详细展开

这一部分是一份**面试官学习讲义**，应当能独立阅读，不依赖后面的题库才能理解。先给技术知识地图和推荐学习顺序，说明技术之间的依赖与联系，再按技术点或紧密关联的技术组展开。候选人的简历决定讲解入口，不限制必要的背景知识；新增背景明确标成学习补充，不能算作候选人的经历。

### 面向面试官的讲解方式

- 默认读者具备一般软件开发常识，但不熟悉该技术栈。先补当前概念真正依赖的前置知识；缩写首次出现给出全称、中文含义和具体作用，避免用另一个未解释的术语解释术语。
- 按“为什么需要 → 直观理解 → 严格定义 → 核心机制 → 具体例子 → 选型与边界”讲解。类比只帮助入门，随后交代类比不能覆盖的实际机制。
- 核心技术至少用一个贯穿的小例子，从输入、中间状态到输出走完整过程。复杂机制可用简图、分步数据、伪代码或必要公式解释；公式须说明变量、直觉及一个简单计算，代码须解释关键步骤，不能堆砌实现细节。
- 专门辨析容易混淆的相邻概念，按解决的问题、输入输出、处理阶段、成本和限制比较；例如召回/重排、RAG/微调、工作流/Agent、并发/并行。只比较与当前材料有关的概念。
- 不只说“更快”“更准”“更可靠”，解释收益产生的机制、成立条件、代价和反例。默认参数与数字仅作例子，标明不是普遍最优值；某个框架的默认实现不能代表该技术的唯一定义。
- 每个核心技术末尾给面试官的“理解自检”：用自己的话应能解释什么、一个短思考题及其讲解要点。自检服务于面试官学习，与后面的候选人面试题分开。
- 最后给分层学习顺序：先理解哪些基础，再串起哪条完整链路，有时间再深入哪些机制；可以附一个无需真实业务数据的小练习。若提供延伸资料，优先官方文档、原论文或维护者资料，并标注版本/核验状态；未核验的链接和 API 不编造。

在上述教学结构中覆盖以下内容，让面试官理解“是什么、如何工作、在这个项目里为什么有用、如何考察”：

1. **原文依据与学习目标**：用短引文说明为什么讲这个技术，并写出面试官学完应能解释的问题；候选人声称的了解、使用、设计、优化、负责等深度单独标注，不用它代替知识讲解。
2. **概念与问题**：用易懂语言解释定义、解决的问题、适用边界；不能只翻译缩写或罗列同类产品。
3. **关键机制**：展开必要的执行流程、数据流、状态或接口；用具体小例子、伪代码或简短流程帮助理解。说明框架封装了什么、开发者仍要负责什么。
4. **项目中的可能角色**：联系简历原文解释其作用。架构未给出时明确“待验证的可能实现”，不要写成该项目真实架构。
5. **选型与工程取舍**：讨论有关的替代方案、性能、可靠性、成本、可维护性和边界条件；避免无背景的绝对优劣判断。
6. **常见问题与排障**：给出具体故障表现、可能原因、观察指标或日志、定位路径及可验证的改进方式。
7. **从理解到面试应用**：先完成面试官的理解自检，再说明候选人仅会调用、理解原理、能独立设计和优化分别能提供什么证据；链接到后面的面试题编号。此项是教学后的应用，不替代前面的完整解释。

以下是按需使用的岗位视角，不是每份简历都必须出现的固定清单。只对简历或 JD 涉及的领域作重点展开；岗位相关但未出现的领域单列为“补充考察”，不得混入候选人经历：

- Agent 执行：工具调用与参数 schema、循环与停止条件、工作流/状态机、状态持久化、重试、幂等、副作用、超时、取消、人工介入；能否区分确定性流程与模型决策。
- LLM 应用：结构化输出、上下文管理、流式调用、模型选择与降级、延迟/token/成本预算；区分提示词调优、RAG、微调的适用条件。
- RAG/记忆：切分、embedding、索引、元数据过滤、混合检索、rerank、上下文组装、更新一致性和权限过滤；区分检索质量与生成质量、短期状态与长期记忆。
- 工具协议与编排：MCP、框架或多 Agent 的职责边界、接口契约、状态传递、协调开销和故障传播；追问为什么单 Agent 或普通工作流不够。
- 评测与生产：数据集与基线、成功定义、端到端成功率、工具调用正确性、回归、在线反馈、trace、故障恢复、可观测性与发布回滚。
- 后端基础：与项目有关的 Python/TypeScript、异步并发、HTTP/SSE/WebSocket、数据库/事务、缓存、消息队列、容器部署；将基础问题放回实际请求链路。
- 权限与安全：提示注入、数据与指令边界、身份与授权、工具执行范围、沙箱、密钥及个人数据处理；通过具体项目风险考察。

如技术机制依赖具体版本，先说明版本未知；确需核实版本或新 API 时查官方文档并引用来源。不要为了背景检索把完整简历、联系方式或内部项目资料发送给搜索服务。

## 主体二：由浅入深的面试题与考核方向

题目必须锚定技术点 Tn、项目 Pn 或 JD 的具体要求，并提供面试官可判别回答质量的内容。分为两条相互关联的线，不能只给基础八股题，也不能只有项目介绍题。

### A. 技术深度线

围绕核心技术组织连续问题链：

- **L1 基础理解**：定义、输入输出、关键流程、最小例子；判断是否理解而非只记术语。
- **L2 实现与排障**：结合简历中的用法，询问接口、数据结构、状态、配置、故障定位，必要时要求伪代码；判断是否实际实现过。
- **L3 设计与取舍**：改变规模、约束或故障条件，追问替代方案、评测和恢复设计；判断独立设计、验证与优化能力。

每条问题链都要包含可直接问出口的题干，而不是“考察 RAG”“追问并发”等标签。深题沿前题展开；若基础不清楚，给降阶澄清题，不机械跳到高级术语。

### B. 项目深度线

对每个实质项目建立递进问题链。优先详问与岗位最相关、声称个人贡献最大或结果最需要核实的项目：

- **L1 还原项目和职责**：用户问题、约束、请求的完整流转、本人负责的模块和边界、与团队已有能力的区别。
- **L2 验证实施细节**：沿一条真实请求追到模型、工具、数据与返回；追问本人做过的关键改动、失败案例、日志/trace、数据或接口设计、如何测试。
- **L3 验证结果和设计能力**：原方案与替代方案、为什么选择、数字如何测得、基线和样本如何设定、回归与上线、极端情况和故障恢复；再用一个明确标注为假设的约束变化验证迁移能力。

对于“提升 X%”“高并发”“自主 Agent”等表述，设计能区分产品描述、团队成果和个人贡献的具体问题。保持中立；信息缺失或表述模糊是待验证点，不直接判定造假。

### 每道主问题的交付字段

- **编号 / 来源 / 深度 / 优先级**：例如 Q-P1-02，关联 P1/T3，L2，必问或选问。
- **具体题干**：明确情境与问题，不一次堆叠太多不相关子问。
- **重点考核方向**：说明希望区分哪种能力，与 Agent 开发岗位有什么关系。
- **参考回答要点与判别信号**：列出应覆盖的机制、证据、权衡或实现细节，解释什么是基本合格、深入回答，以及哪些回答需要继续核实。参考要点不是候选人的实际答案，也不是唯一合法方案。
- **递进追问**：回答清楚时如何加深；回答抽象或不清楚时如何要求例子、边界或最小实现。
- **需核验的证据**：如脱敏架构图、伪代码、评测设计、指标计算过程或故障复盘。不要要求展示前雇主机密、访问凭据或个人数据。

每道主问题都使用以上字段，技术线和项目线一视同仁，不只给第一道题写完整。主问题只标一个 L1/L2/L3 等级，更深的问题放入递进追问；不要用“L2/L3”掩盖未展开的深度。如果篇幅受限，减少重复备选题，仍保留核心技术的三级问题链及每题的判断依据。不同合理实现都可以成为强回答，不能因未采用某框架、某算法或无法披露源码就判定没做过。并发取消、框架默认行为等版本敏感细节不要写成无条件通则。

默认按简历复杂度选题，不为凑数量重复同一知识点。确保核心技术和实质项目均有递进覆盖；在详尽题库前列出一条优先面试路径。若未给时长，可提供“建议 60 分钟，可调整”的时间安排，注明哪些必问、哪些作为深入备选。不能暗示全部备选题都能在建议时长内完成。

“必问”应与优先面试路径一致：未排入本轮时长的题标为选问或替换题，不在题库写必问、又在路径中写按时间选做。引用的题号必须实际存在且无重复；为开场、切换和候选人提问留出时间。

## 最终组织与判断边界

建议按以下顺序输出，适度使用表格作索引，技术机制和多层追问用短段落完整解释，避免挤进难读的宽表格：

1. 岗位假设、材料覆盖范围和简历证据索引。
2. 面试官学习讲义：知识地图、技术点详细展开、易混概念对比、理解自检和学习顺序。
3. 技术面试问题链。
4. 逐项目面试问题链。
5. 重点考核方向与优先面试路径：优先级、原文依据、需验证的能力、关联题号和强/弱证据信号。
6. 尚待补充或核实的信息。

当前若只有简历而没有面试回答，只评估证据充分程度和考察优先级，不假定候选人已经答对，不凭术语数量打出能力分。用户要求评分时说明评分依据和未知项；不自动给出录用或淘汰决定。不依据年龄、性别、婚育、民族、健康等与岗位无关的个人属性评价。输出不重复不必要的联系方式。

提交前自查：两个主体是否完整；不熟悉该技术的面试官能否仅凭第一部分理解机制、例子和取舍；是否误把学习讲义写成考点清单；技术点有没有漏掉或只列名；问题是否真正来自该简历；L1→L2→L3是否递进；技术与项目两条线是否均覆盖；每道主问题是否有考核方向、参考要点和追问；是否把推测误写为经历；优先路径是否可执行。
